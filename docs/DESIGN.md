# 设计文档 · 为什么这么做

## 1. 要解决的问题

AI 通过 MCP 改引擎界面时，只有文字。它知道「有个按钮」，不知道按钮在屏幕的哪里、
和谁对齐、用户说的「这个」指哪一个。于是常见失败是：改对了属性，改错了对象/位置。

本软件把「位置」变成机器可读的数据：**像素矩形 + 提示词 + 挪动位移**，
并让 AI 用**它熟悉的通道（MCP）**拿到这些数据。

## 2. 形态选择

| 方案 | 结论 |
| --- | --- |
| Electron 桌面应用 | ✅ 采用。能直接枚举系统窗口、按窗口抓图、把目标窗口切前台，这是「反复截同一个编辑器」的关键 |
| 纯浏览器页面 | ❌ 每次截图都要手动选窗口，拿不到窗口列表，也切不了前台 |
| 引擎插件（Godot/Unity Editor 插件） | ❌ 只能服务单一引擎，且用户往往同时改 UI 与网页；插件还要各自维护 |

## 3. 架构

```
┌──────────────────────────── Electron 主进程 ────────────────────────────┐
│  main.js            窗口生命周期 / IPC / 日志                            │
│  capture.js         窗口枚举与置前(powershell 助手) + 两条抓图链路        │
│  api.js             全部业务操作的唯一实现（IPC 与 HTTP 共用）            │
│  bridge.js          127.0.0.1 回环 HTTP + token（MCP 的接入面）           │
│  store.js           会话落盘（纯 Node，可离线/被 MCP 直读）               │
└───────────────┬───────────────────────────────────┬────────────────────┘
                │ contextBridge(白名单)              │ HTTP(port+token)
        ┌───────┴────────┐                  ┌───────┴─────────┐
        │  渲染进程        │                  │  MCP stdio 服务  │
        │  画布编辑器      │                  │  AI 客户端       │
        │  提示词卡片      │                  └─────────────────┘
        └────────────────┘
```

**关键决策：业务逻辑只有一份。** `api.js` 的 `dispatch(op,args)` 同时被 IPC 和 HTTP 调用，
渲染进程与 AI 走的是完全相同的代码路径，不存在「界面能存、AI 存不了」这种分叉。

**为什么 MCP 服务要经过回环 HTTP，而不是直接读写文件？**
- 截图、裁切、枚举窗口这些操作必须在持有 Electron 上下文的进程里做（`desktopCapturer`、`nativeImage`）；
- 独立 stdio 进程无法持有这些能力，所以它做一个薄代理；
- 顺带得到一个可被脚本/自检使用的自动化入口（本项目所有端到端测试都走这条路）。

**为什么零原生依赖？** `better-sqlite3` 这类模块的 ABI 与 Electron 不一致是打包事故高发区。
会话数据量很小（每会话几百条标注），JSON 文件足够，换来的是「装完就能跑」。

## 4. 数据模型

```jsonc
{
  "id": "cap-20261028-232016-0wip",
  "createdAt": "…", "updatedAt": "…", "status": "open",
  "source": {                       // 来源窗口信息，AI 换算坐标要用
    "kind": "window", "title": "主场景 - Godot", "process": "godot.exe",
    "hwnd": "0x110986", "rect": { "x": 1274, "y": 253, "w": 1028, "h": 621 },
    "display": { "bounds": {…}, "scaleFactor": 1 },
    "method": "window-source",      // window-source | screen-crop，便于排查
    "foreground": true,             // 是否成功置前（false 时截图可能含遮挡）
    "requestedBy": "ai"             // ai = 由 MCP 请求，界面会自动切过去
  },
  "image": { "file": "base.png", "width": 1028, "height": 619 },
  "annotations": [
    { "id": "ann-…", "type": "box", "rect": { "x": 120, "y": 90, "w": 260, "h": 120 },
      "prompt": "把这个面板改成深色、宽度 320", "color": "#ff5d5d",
      "status": "pending", "aiNote": "" },
    { "id": "ann-…", "type": "move",
      "from": { "x": 60, "y": 300, "w": 180, "h": 60 },   // 原位置
      "to": { "x": 420, "y": 620 },                        // 目标左上角
      "prompt": "把这条工具栏挪到右下角", "color": "#4f9dff",
      "status": "done", "aiNote": "已改到右下角" }
  ]
}
```

`move` 只存 `from/to`（不存 `rect`），位移由 `to - from` 派生，避免两处数据打架。

### 并发写入策略（重要）

界面会整体保存整个标注数组，AI 会单独回写某条的 `status/aiNote`。两者必然打架。规则：

> **提示词与几何以界面为准；状态与 AI 备注以磁盘为准。**

`store.saveAnnotations()` 按 id 合并时，强制保留磁盘上的 `status / aiNote / createdAt`。
这样用户在编辑提示词时不会把 AI 的「已完成」擦掉，AI 回写也不会冲掉用户没保存的输入。

界面侧再用 2.6 秒轮询把磁盘上的状态差异合并回来（并同步 AI 新加的标注），
所以 AI 改完 3 秒内用户就能看到变绿。

## 5. 两条截图链路

```
置前目标窗口 ──► ① desktopCapturer window source（按标题匹配）
                      │  尺寸 ≈ 窗口矩形？非纯黑？宽高比一致？
                      │  是 → 用它（窗口自身的画面，最干净，含被遮挡的情况）
                      └─ 否/失败
                          ▼
                 ② 抓整个屏幕 → 按窗口矩形裁剪（需要置前成功）
```

- 尺寸/宽高比/纯黑三重校验，是为了防止拿到「缩略图」或「GPU 窗口黑图」；
- `method` 字段把实际走的链路写进会话，出问题时不用猜；
- 置前用 `AttachThreadInput + SetForegroundWindow`，并**只在窗口最小化时**才 `SW_RESTORE` ——
  对最大化窗口调用 `SW_RESTORE` 会把它缩成小窗（本项目实测踩过，已修）。

## 6. 坐标约定（AI 落地时最容易错的地方）

- 所有坐标以**截图左上角**为原点，单位像素，x 向右、y 向下；
- 窗口截取时，截图就是窗口可见区域，等价于客户区（Windows 圆角/阴影已用 DWM 扩展边框扣除）；
- 写给 AI 的文档里明确要求：换算到引擎坐标系（左下角原点、锚点、DPI 缩放）时**必须整体平移/缩放后再套用**；
- 结构化数据里额外给出 `center` 与 `dx/dy`，减少 AI 自己算错的概率。

## 7. 已知技术债 / 明确没做

- 窗口枚举与置前是 Windows 专属（PowerShell + user32）；其他平台只能整屏。
- 多显示器混合 DPI 下，屏幕裁剪兜底路径的坐标换算只做了「按中心点选显示器 + 比例换算」，
  极端布局可能偏移（窗口直取路径不受影响）。
- 没有做「同一窗口的二次截图 diff 对比」（用户本轮未选），但数据结构已留 `source.rect`，后续可加。
- 没有做引擎侧自动应用（那属于 AI + 引擎 MCP 的职责）。
